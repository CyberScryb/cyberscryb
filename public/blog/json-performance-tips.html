10 Performance Tips for Working with Large JSON

By CyberScryb Team · April 5, 2026 · 7 min read

JSON is a lovely serialization format right up until your file breaks the 100MB barrier. At that point, the same JSON.parse() call that you have been happily using for a decade will allocate 3–5x the file size in memory, pause your event loop for several seconds, and occasionally crash the process with an out-of-memory error. If you have ever tried to load a real database export in Node.js or a pandas notebook, you know the feeling.

Here are ten practical tips for handling JSON when the file is too big, too slow, or too weird for the default parser. No theory — every one of these has saved us real time on real projects.

1. Use NDJSON (newline-delimited JSON) instead of one big array

The single biggest unlock for large JSON is switching from [{...}, {...}, ...] to one-object-per-line NDJSON. NDJSON lets you stream-process records one at a time, never holding the full dataset in memory. Every modern tool in the ecosystem (jq, DuckDB, pandas, ClickHouse, ripgrep) handles NDJSON natively.

Rule of thumb: if the file will ever exceed 10MB, emit NDJSON from the start.

2. Switch to a streaming parser

Even with a big single-array JSON file, you can use a streaming parser like stream-json (Node.js), ijson (Python), or json-stream-parser in your language of choice. These parsers emit events as they walk the syntax tree, so you can process each record as it is discovered without ever materializing the whole document.

The trade-off: streaming parsers are harder to use for deeply nested lookups. If you need to ask "for record X, give me the fifth nested field," a streaming parser is awkward. If you need to ask "iterate over all records and do something," streaming wins every time.

3. Flatten nested paths before you analyze

If you are going to do any real analysis on the data, flatten nested objects into dot-separated columns (user.address.city) before you load them into a dataframe or spreadsheet. Flattening trades a little memory for an enormous ergonomic improvement and unlocks every tabular tool in existence.

Our JSON to CSV converter does this automatically — paste nested JSON and get flat columns, even for arrays of sub-objects. It handles files up to 50,000+ rows in the browser without hitting a server.

4. Use DuckDB for ad-hoc queries

DuckDB is the underrated weapon for JSON work in 2026. It can read NDJSON and nested JSON directly, run SQL against it, and handle multi-gigabyte files on a laptop. One line:

duckdb -c "SELECT * FROM read_json_auto('huge.ndjson') WHERE country='US'"

That one command will happily process a 2GB NDJSON export in seconds, where JSON.parse would have exploded.

5. Store numbers as numbers, not strings

JSON is forgiving about types, which means you can store a timestamp as "1712920000000" just as easily as 1712920000000. The string version costs ~3x the bytes and forces a reparse on every use. When you generate JSON, use native numeric types. When you ingest JSON, cast strings to numbers at the earliest possible step so downstream code does not pay the tax repeatedly.

6. Drop fields you do not need at the parse boundary

Most large JSON files have a handful of tiny fields you actually care about and a dozen huge fields you do not. A 1KB-per-record blob becomes a 20MB file in ten thousand records. If you can strip the unused fields at the parse boundary — either with a streaming parser's visitor, a jq filter, or a DuckDB SELECT col1, col2 — you save memory, CPU, and downstream processing time.

Cheap cheat: jq '.[] | {id, name, email}' big.json > small.ndjson produces a slim NDJSON from a bloated array.

7. Convert to a columnar format for repeated analysis

If you are going to run more than three queries against the same JSON file, convert it to Parquet or Arrow once and re-use the columnar file. Parquet files are typically 10–20x smaller than the equivalent JSON and 50–100x faster to query because columnar stores only read the columns you ask for.

DuckDB can do the conversion in one line: COPY (SELECT * FROM read_json_auto('big.json')) TO 'big.parquet' (FORMAT PARQUET). After that, every subsequent query is fast enough that you forget the file was ever slow.

8. Avoid pretty-printed JSON at scale

Pretty-printed JSON is great for humans reading small files. It is awful for large files. The extra whitespace inflates file size by 20–40% and costs every downstream parser time to skip over. In production pipelines always emit minified JSON; keep pretty-printing for ad-hoc inspection tools, not for storage.

9. Use JSON.parse's reviver parameter (carefully)

In JavaScript, the second argument to JSON.parse is a reviver function called for every key-value pair during parsing. You can use it to transform values on the fly (parse date strings into Date objects, convert big numeric strings to BigInt) without a second pass. The catch: the reviver is called even for fields you do not care about, so it is only a win when most fields need transformation.

10. Use the right tool for the right job

A summary of when to reach for what:

  • Under 1MB: just use the built-in parser, you are fine.
  • 1–50MB: a browser-based tool like CyberScryb JSON↔CSV or online formatter still works; watch memory.
  • 50MB–1GB: switch to NDJSON + DuckDB or a streaming parser.
  • 1GB+: Parquet + DuckDB or a columnar warehouse; do not try to load the raw JSON into memory.
  • Nested and gnarly: flatten first, analyze second.

A worked example

Here is a real example from a recent project. We had a 680MB JSON export from a third-party CRM, structured as one giant array of user objects with nested activity arrays. The naive Node.js approach (JSON.parse(fs.readFileSync(...))) allocated 3.2GB of memory and crashed.

The fix was three lines of jq:

jq -c '.[] | {id, email, last_login}' export.json > users.ndjson
duckdb -c "COPY (SELECT * FROM read_json_auto('users.ndjson')) TO 'users.parquet' (FORMAT PARQUET)"
duckdb -c "SELECT COUNT(*) FROM 'users.parquet' WHERE last_login > '2025-01-01'"

The first command peeled the JSON into a slim NDJSON in under a minute. The second produced a 24MB Parquet file. The third answered the business question in 0.08 seconds. From a crash to an answer in three commands.

The takeaway

Large JSON is not a data problem — it is a tooling problem. The moment you reach for NDJSON, streaming parsers, DuckDB, and Parquet, every "my JSON won't fit in RAM" story disappears. Start with the smallest change that unlocks the most leverage (step 1: switch to NDJSON) and add the rest as you hit the next wall.
