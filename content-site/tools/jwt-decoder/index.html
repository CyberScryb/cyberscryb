How to Decode a JWT

  1. Copy the token. Grab it from your Authorization header, cookie, or log. If it starts with Bearer , strip that word off and paste only the token itself.
  2. Paste it above. The decoder splits the token on its two dots and Base64URL-decodes the header and payload into readable JSON the moment you paste. No button to press.
  3. Read the claims. Check the algorithm in the header, then the payload: who it is for (sub, aud), who issued it (iss), and whether it is still alive (exp). The metadata bar converts the Unix timestamps into plain dates and flags an expired token in red.

Stuck with a token that will not decode? Either it is truncated, it has more or fewer than three dot-separated parts, or one part is not valid Base64URL JSON. Copy it again from the source instead of retyping it — a single missing character breaks the whole string.

What Is a JWT? The Three Parts

A JSON Web Token (RFC 7519) is a compact, URL-safe way for one party to send claims to another. Every JWT is three Base64URL-encoded segments separated by dots: header.payload.signature.

Header. Names the signing algorithm (alg, usually HS256 or RS256) and the token type (typ, usually JWT). It may also carry a key id (kid) telling the verifier which key to use.

Payload. The claims: statements about the user and the token itself, such as the subject, issuer, audience, and expiry. This is the part you are usually debugging.

Signature. Created by signing the header and payload with a secret or private key. It proves the token was not altered after it was issued. This decoder shows the raw signature segment but does not verify it — verification needs the key and belongs on your server.

The part most people get wrong: a JWT is signed, not encrypted. Base64URL is an encoding anyone can reverse, so anyone holding the token can read the payload. Never put passwords, personal data, or secrets in a JWT. If the contents must stay secret, use an encrypted token (JWE) instead.

Standard JWT Claims

RFC 7519 defines seven registered claims. No token carries all of them, but when they appear, this is what they mean. The time claims (exp, nbf, iat) are Unix timestamps in seconds since January 1, 1970 UTC, not milliseconds.

ClaimNameWhat it means
issIssuerWho created the token. A verifier should only accept issuers it trusts.
subSubjectWho the token is about, usually a user id.
audAudienceWho the token is intended for, usually your app or API.
expExpiration timeUnix timestamp after which the token must be rejected.
nbfNot beforeUnix timestamp before which the token is not valid yet.
iatIssued atUnix timestamp when the token was created.
jtiJWT IDA unique id for the token, used to track or revoke individual tokens.

Who Uses a JWT Decoder

Debugging a 401. An API returns Unauthorized and the token looks fine. Decode it and the answer is usually in the claims: the wrong audience, the wrong issuer, or an exp that passed an hour ago.

Checking expiry before a demo or deploy. Paste the token you are about to use and read the expiry date in plain English instead of doing Unix-timestamp math in your head.

Inspecting roles and scopes. Identity providers stuff custom claims into the payload: roles, permissions, tenant ids, email. Decoding shows exactly what your app will see when it parses the same token.

Learning how auth works. A JWT is the fastest way to see a real auth token from the inside. Paste the sample token with the Load Sample button and watch the header, payload, and signature fall apart into readable pieces.

Decoded Does Not Mean Valid

Decoding only reads a token. It does not prove the token is genuine, unexpired, or meant for you. A token with a valid-looking payload and a forged signature decodes perfectly and should still be rejected. Validation means checking the signature with the secret or public key, then enforcing exp, nbf, iss, and aud — all of that happens on your server, never in a decoder.

Treat live tokens as credentials. Prefer an expired token, a test token, or the built-in sample when you can, and never paste a private key into any online tool.

Frequently Asked Questions

What is a JWT?

A JSON Web Token is a compact, URL-safe token format used to transmit claims between two parties. It is made of three Base64URL-encoded parts separated by dots: header, payload, and signature.

Does this tool verify JWT signatures?

No. This tool only decodes the token to display its contents. Verifying a signature requires the signing secret or public key and must be performed on a trusted backend.

Is it safe to paste tokens here?

Yes — decoding is done entirely in your browser. Your token is never sent over the network. Still, avoid pasting real production tokens into any third-party tool when you can avoid it.

What do iat, exp, and sub mean?

iat is "issued at" (Unix timestamp when the token was created). exp is the expiration timestamp. sub is the subject — typically a user identifier.

Can I edit a JWT without breaking it?

No. Any change to the header or payload invalidates the signature. A properly configured server will reject any modified token.

Can I decode a JWT without the secret key?

Yes. The header and payload are only Base64URL-encoded, not encrypted, so anyone can decode them. The secret key is only needed to verify the signature — decoding never requires it.

Is a JWT encrypted? Can anyone read the payload?

No, a standard JWT is signed, not encrypted. Base64URL is an encoding anyone can reverse, so anyone holding the token can read the payload. Never put passwords, personal data, or secrets in a JWT — if the contents must stay secret, use an encrypted token (JWE) instead.

How do I check if a JWT is expired?

Decode the token and read the exp claim, a Unix timestamp in seconds. This decoder converts it to a readable date and flags it as expired or still valid. An expired token still decodes normally — expiry only matters when a server validates it.
